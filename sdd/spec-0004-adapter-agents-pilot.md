# Пилотные инструкции для агентов репозитория kafka-adapter

## Краткое описание

- Создать самодостаточный англоязычный `AGENTS.md` в репозитории `kafka-adapter`.
- Согласовать структуру пилотного файла до создания инструкций в остальных репозиториях экосистемы.
- Хранить знания о продукте и архитектуре в документации репозитория, а в `AGENTS.md` оставить операционные правила для агентов.
- Все SDD вести на русском языке.

## Контекст

Экосистема размещена в одном рабочем каталоге как несколько независимых Git-репозиториев. Существующий Memory Bank планируется удалить после переноса уникальных знаний в документацию репозиториев или в локальные инструкции для агентов. SDD и ADR останутся в `tasks/sdd` и `tasks/adr`.

## Проблема

Агентам нужны краткие инструкции внутри репозитория, применимые и при отдельном клонировании `kafka-adapter`. Инструкции должны запрещать полное сканирование репозитория, неверную маршрутизацию между metadata tools, небезопасное прямое редактирование исходников 1С и изменения без проверки.

## Цель

Добавить `adapter/adapter/AGENTS.md` как согласованный пилот. Файл должен определять область репозитория, ограниченную навигацию, правила изменения 1С, проверки, обязанности по документации, требования SDD/ADR, сетевые ограничения и правила безопасности.

## Не входит в задачу

- Не создавать в рамках этой спецификации `AGENTS.md` в остальных семи репозиториях.
- Не удалять и не переносить существующий Memory Bank.
- Не изменять исходники продукта, метаданные, тесты, CI или документацию продукта.
- Не определять новую архитектуру продукта или поведение публичного API.

## Область изменений

- Добавить только `adapter/adapter/AGENTS.md` в репозиторий продукта.
- Хранить эту спецификацию в `tasks/sdd`.
- Согласовать пилот перед использованием его структуры для остальных репозиториев.

## Функциональные требования

### Назначение репозитория и источники истины

- Определить `kafka-adapter` как репозиторий расширения/библиотеки продукта и его документации.
- Считать актуальные локальные исходники 1С и тесты первичными источниками фактического поведения.
- Считать документацию репозитория каноническим сопровождаемым описанием продукта, если она не противоречит актуальным исходникам или тестам.
- Сохранять оригинальные русские идентификаторы 1С.

### Навигация и ограничение контекста

- Не выполнять рекурсивное сканирование всего репозитория.
- Начинать с `README.md`, известных путей, документации репозитория, ограниченных metadata-запросов или пути, указанного пользователем.
- Ограничивать количество результатов и запрашивать только необходимые объекты, методы, разделы или диапазоны строк.
- Не загружать модуль целиком, если достаточно меньшего фрагмента.
- Если расположение нужного кода неизвестно, запросить у пользователя каталог или файл вместо сканирования репозитория.

### Маршрутизация MCP

- Использовать доступные MCP-сервисы по назначению.
- Использовать `kfk_edt` как актуальный интерфейс к текущему 1С-проекту `kafka-adapter`.
- Использовать `code-metadata-mcp` и `graph-metadata-mcp` только для навигации и анализа влияния в `adapter/adapter`.
- Не считать навигационные индексы актуальным состоянием проекта, если они противоречат `kfk_edt`.
- Использовать `SyntaxCheckServer` для проверки изменённого BSL-кода.
- Использовать `HelpSearchServer` для справки по синтаксису 1С и API платформы.
- Использовать `v8std` как базовый стандарт разработки 1С, включая код, методы, идентификаторы, процедуры, функции, переменные и объекты метаданных.
- В пределах допустимых правил `v8std` сохранять сложившийся стиль исходников.

### Редактирование

- Любые файлы 1С в `src/**` изменять только через `kfk_edt`.
- Если `kfk_edt` недоступен, сообщить об ошибке и не редактировать исходники 1С напрямую.
- Не обходить ограничение прямым текстовым изменением `.bsl`, `.mdo`, `.form`, `.rights`, XDTO или других файлов в `src/**`.
- Для новых объектов метаданных 1С, принадлежащих этому репозиторию, использовать префикс `кфк`.
- Файлы, не относящиеся к исходникам 1С, можно изменять напрямую в UTF-8 с сохранением существующего стиля и формата окончания строк.
- Не изменять вручную сгенерированные release artifacts и отчёты.

### Проверки

- После изменения 1С выполнять ограниченную диагностику EDT, проверку изменённого кода через `SyntaxCheckServer` и `v8std`.
- Запускать соответствующие YAxUnit- или UI-тесты, если изменённое поведение ими покрыто и необходимое окружение доступно.
- Явно указывать, какие проверки не удалось выполнить и почему.
- Учитывать возможные ложные срабатывания EDT diagnostics. Если diagnostic не удалось устранить за одну итерацию исправления, остановиться и спросить пользователя, как обработать ошибку, вместо повторных изменений кода.

### Требования SDD и ADR

- Требовать утверждённый SDD для нетривиальных изменений поведения, публичного API, схем данных и нескольких репозиториев.
- Агент может создать SDD со статусом `draft`, но не должен начинать реализацию до явного утверждения пользователем.
- Для уже утверждённого SDD дополнительное подтверждение реализации не требуется.
- Не требовать SDD для локального bug fix, точечного теста, изменения только документации или обычного исправления tooling, если оно не меняет перечисленные контракты.
- Создавать ADR только для долгосрочного архитектурного решения или изменения границ компонентов.
- Изменять несколько репозиториев только при явно заданной пользователем multi-repository scope или если они перечислены в утверждённом SDD.
- Все SDD писать на русском языке; технические identifiers, команды и пути оставлять без перевода.

### Документация и завершение задачи

- Вместе с изменениями публичного API, конфигурации, deployment, ограничений или пользовательского поведения обновлять документацию репозитория.
- Не обновлять документацию продукта при внутреннем refactoring без изменения поведения.
- Фиксировать в утверждённом SDD результат реализации, выполненные проверки, непроверенные аспекты и отклонения.
- Обновлять ADR только при изменении принятого решения.

### Сеть и безопасность

- Ограничение скачивания действует на любые артефакты из глобального интернета, включая прямые загрузки, зависимости package manager, release artifacts и слои container images.
- Если размер артефакта превышает 100 MB или его невозможно определить до начала загрузки, не начинать скачивание. Попросить пользователя предоставить артефакт локально или явно разрешить загрузку.
- Разрешено использовать локально закэшированные файлы и образы.
- Не раскрывать, не коммитить и не помещать в результаты или файлы репозитория secrets, tokens, credentials и личную конфигурацию.
- Не выполнять destructive operations без явного разрешения пользователя.

## Нефункциональные требования

- `AGENTS.md` должен быть написан на английском языке в корректном Markdown.
- Файл должен быть достаточно кратким для чтения в начале задачи и самодостаточным для отдельного клона.
- Использовать пути относительно репозитория; не добавлять абсолютные пути рабочего окружения.
- Не копировать в `AGENTS.md` архитектурную, API- и пользовательскую документацию; вместо этого ссылаться на локальную каноническую документацию.
- Явно указывать ограничения и недоступные проверки.

## Архитектура и дизайн

Использовать один `AGENTS.md` в корне репозитория. Разделы должны кратко описывать назначение репозитория, ограниченную навигацию, маршрутизацию tools, редактирование, проверки, workflow SDD/ADR, документацию и безопасность. Специфичные для репозитория правила имеют приоритет над общими соглашениями, если не противоречат инструкциям пользователя.

При дальнейшем распространении можно повторно использовать структуру разделов, но каждый репозиторий должен получить только относящиеся к нему правила. Для generated reports, UI-тестов, unit-тестов, Conversion Data, examples, base configuration и infrastructure tools нужны разные правила изменения и проверки.

## План реализации

1. Подготовить `adapter/adapter/AGENTS.md` по утверждённым требованиям.
2. Проверить самодостаточность файла, ограничения навигации, точную маршрутизацию MCP и отсутствие противоречий.
3. Убедиться, что в `kafka-adapter` изменён только новый `AGENTS.md`.
4. Зафиксировать результат реализации и проверки в этой SDD.
5. Перед подготовкой файлов для остальных семи репозиториев представить пилот пользователю.

## Совместимость и миграции

Пилот добавляет только инструкции и не меняет runtime behavior. Последующее удаление Memory Bank и перенос каталогов SDD/ADR требуют отдельной утверждённой спецификации, поскольку меняют структуру документации и ссылки.

## Проверка

- Проверить структуру Markdown и кодировку UTF-8.
- Убедиться, что все пути указаны относительно репозитория.
- Сверить названия tools и правила маршрутизации с утверждёнными требованиями.
- Убедиться, что ни одно правило не разрешает прямое редактирование файлов в `src/**`.
- Убедиться, что при неизвестном расположении кода требуется запросить путь у пользователя, а не сканировать весь репозиторий.
- Убедиться, что сетевое правило блокирует неразрешённые загрузки свыше 100 MB и загрузки с неизвестным размером.
- Проверить `git diff -- AGENTS.md` в `kafka-adapter`.

## Риски

- Избыточное повторение знаний о продукте приведёт к устареванию инструкций; риск снижается ссылками на локальную документацию.
- Строгая зависимость от `kfk_edt` блокирует изменения 1С при недоступности сервиса; это намеренное ограничение.
- EDT diagnostics могут давать ложные срабатывания; правило одной итерации ограничивает спекулятивные исправления.
- В отдельном клоне может отсутствовать `tasks/sdd`; агент должен сообщить об отсутствии координационного репозитория, а не создавать другое каноническое расположение.

## Критерии приёмки

- `adapter/adapter/AGENTS.md` существует и написан на английском языке.
- Файл содержит все функциональные правила этой спецификации и не противоречит README репозитория или инструкциям пользователя.
- Файл самодостаточен и не требует Memory Bank для обычной работы.
- Запрещены полное сканирование репозитория и прямое редактирование исходников 1С в `src/**`.
- Определены точная маршрутизация MCP и обязательный набор проверок.
- Определены требования SDD/ADR, обязанности по документации, сетевые ограничения и эскалация diagnostics.
- Исходники продукта, тесты, CI, generated artifacts и документация продукта не изменены.

## Открытые вопросы

Блокирующих вопросов нет. Перед реализацией пользователь должен утвердить структуру пилота.

## Результат реализации

Создан `adapter/adapter/AGENTS.md` на английском языке. Файл содержит:

- назначение репозитория и приоритет источников;
- запрет полного рекурсивного сканирования и правила ограниченной навигации;
- маршрутизацию `kfk_edt`, `code-metadata-mcp`, `graph-metadata-mcp`, `SyntaxCheckServer`, `HelpSearchServer` и `v8std`;
- запрет прямого редактирования любых файлов 1С в `src/**`;
- префикс `кфк` для новых объектов метаданных;
- обязательные проверки и эскалацию EDT diagnostics после одной итерации исправления;
- workflow SDD/ADR, обязанности по документации, сетевой лимит и правила безопасности.

Выполнены проверки:

- файл прочитан строгим UTF-8 decoder без ошибок;
- проверена структура Markdown headings;
- точечно подтверждено наличие всех обязательных правил;
- `git status` репозитория `kafka-adapter` показывает только новый `AGENTS.md`;
- исходники `src/**`, тесты, CI, generated artifacts и документация продукта не изменялись.

Пользователь подтвердил структуру пилота 2026-08-03. Пилот можно использовать как основу для репозиторий-специфичных инструкций остальных семи репозиториев.
