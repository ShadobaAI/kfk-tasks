# Устранение проблем BSL по результатам SonarQube

## Summary

- Классифицировать все замечания SonarQube по BSL-коду `kafka-adapter`.
- Исправить подтверждённые дефекты и обоснованно исключить ложные срабатывания.
- Ввести воспроизводимый контроль, запрещающий появление новых BSL-проблем.
- Не изменять требования, метрики и артефакты покрытия кода в рамках этой спецификации.

## Context


GitHub Issue #50 от 2026-07-14 фиксирует 1527 проблем и требует исправить замечания, исключить ложные срабатывания и не допускать новых проблем.

Текущий снимок локального SonarQube `http://ia11:9000`, проект `kafka-adapter`, последнее проанализированное состояние от 2026-07-14, на 2026-07-29 содержит:

| BUG | 29 |
| CODE_SMELL | 982 |
| VULNERABILITY | 0 |

Расхождение между 1527 в issue и 1011 в текущем снимке должно сохраняться в отчётности как изменение baseline, а не интерпретироваться как результат будущей реализации без подтверждения по истории анализов.

Активный quality profile получен непосредственно из SonarQube API: `BSL Language Server rules`, 167 активных правил, profile key `6fd02196-ad9e-4f94-852c-ed2b72f42708`, обновлён 2026-07-09. ## Problem

Текущий backlog смешивает реальные ошибки, сопровождаемость, форматирование, спорные правила и Security Hotspots. Для ложных срабатываний нет единого доказательного процесса. Анализ выполняется в release workflow, но успешный запуск scanner сам по себе не гарантирует прохождение условий качества: workflow не ожидает Quality Gate и не содержит отдельного BSL-gate, независимого от покрытия.

Из-за этого массовое исправление несёт два риска: функциональная регрессия в сложных фоновых и интеграционных модулях и повторное накопление замечаний после очистки baseline.

## Goal

Получить управляемый и проверяемый BSL baseline, в котором каждое исходное замечание имеет одно из состояний:

1. исправлено в коде;
2. подтверждено как ложное срабатывание и исключено минимально возможным способом с обоснованием;
3. явно принято как технический долг с владельцем и отдельной задачей — только как временное отклонение, не как критерий завершения Issue #50.

После завершения новые BSL issues и новые непроверенные Security Hotspots должны блокировать соответствующий CI-контур.

## Non-goals

- Повышение или проверка покрытия кода.
- Изменение `sonar.coverageReportPaths` и генерации coverage XML.
- Исправление условия Quality Gate `new_coverage` или достижение общего статуса Quality Gate `OK`, если единственная причина ошибки относится к покрытию.
- Массовое отключение правил ради уменьшения счётчика.
- Рефакторинг публичного API, модели хранения, протокола Kafka или пользовательского поведения без отдельного требования.
- Обновление SonarQube, Sonar Scanner, BSL Language Server или quality profile без отдельной проверки совместимости.

## Scope

В scope входят:

- BSL-файлы `kafka-adapter/src/**/*.bsl`;
- `.bsl-language-server.json` как каноническая конфигурация BSL-диагностик;
- `sonar-project.properties` только для параметров статического BSL-анализа и точечных исключений;
- SonarQube issue dispositions и review Security Hotspots;
- CI-проверка отсутствия новых BSL-проблем;
- тесты затронутого поведения и отчёт о движении baseline.

## Functional Requirements



### FR-1: Воспроизводимый baseline

Перед исправлениями автоматизированно сохранить обезличенный snapshot без токена:

- дата и идентификатор анализа;
- commit/revision, если SonarQube его предоставляет;
- количество issues по type, severity, rule и component;
- список открытых Security Hotspots и их статусы;
- период New Code;
- версия SonarQube, scanner, BSL-плагина и BSL Language Server, если доступна;
- полный список активных BSL-правил из SonarQube quality profile через API `api/qualityprofiles/search` и `api/rules/search`;
- отдельный список правил, по которым есть открытые issues, через facet `rules` API `api/issues/search`, с количеством по каждому правилу.

Snapshot хранится как Markdown или JSON-артефакт задачи и не должен содержать URL с credentials, токены или Authorization headers.

### FR-2: Приоритизация

Исправления выполняются в порядке:

1. Security Hotspots review и подтверждённые риски;
2. BUG уровня CRITICAL/MAJOR, включая `TimeoutsInExternalResources`, `CreateQueryInCycle`, `DeletingCollectionItem`, `ServerCallsInFormEvents`;
3. проблемы корректности анализа: `QueryParseError`, `AllFunctionPathMustHaveReturn`, `UnusedLocalVariable`, `UnusedLocalMethod`;
4. сложность, вложенность и клиент-серверные вызовы;
5. документирование и дублирование;
6. форматирование, орфография и style-only замечания.

Severity SonarQube не заменяет анализ влияния. Для каждой правки, затрагивающей поведение, должны быть определены функциональные инварианты и регрессионная проверка.

### FR-3: Классификация ложных срабатываний

Замечание может считаться ложным срабатыванием только при наличии воспроизводимого обоснования:

- диагностируемая конструкция корректна для используемой версии платформы 1С;
- правило не учитывает подтверждённый контекст выполнения;
- исправление ухудшает корректность или нарушает обязательный внешний контракт;
- проблема вызвана ошибкой анализатора и подтверждается минимальным примером либо ссылкой на upstream issue.

Предпочтительный порядок исключения:

1. изменить код на однозначный без изменения поведения;
2. применить точечное подавление к конкретной строке или блоку с комментарием;
3. настроить параметр правила для подтверждённого проектного соглашения;
4. исключить конкретное правило для конкретного ресурса;
5. отключить правило глобально только после отдельного согласованного решения с оценкой потери контроля.

Статусы `False Positive` и `Won't Fix` в SonarQube должны сопровождаться комментарием с причиной и ссылкой на код, спецификацию или upstream issue. `Won't Fix` не используется как замена исправлению подтверждённой проблемы.

### FR-4: Пакетная реализация

Один change set должен быть ограничен одним правилом или логически связанным набором правил и небольшим числом компонентов. Для каждого пакета фиксируются:

- исходное и итоговое количество;
- изменённые модули;
- функциональные риски;
- выполненные проверки;
- список подавлений и их основания.

Изменения «механически по шаблону» запрещены, включая безусловную массовую замену, автоформатирование целых модулей и устранение счётчика без анализа контекста. Каждое изменение должно учитывать назначение процедуры, имена предметной области, директивы компиляции и соседний код. После правки код должен оставаться понятным, читабельным и соответствовать текущему стилю конкретного модуля. Форматирование не смешивается с изменением поведения.

### FR-5: Security Hotspots

Все 15 текущих Security Hotspots должны быть просмотрены человеком. Для каждого hotspot фиксируется `Safe` либо подтверждённая проблема с исправлением. Новые hotspots не могут оставаться `TO_REVIEW` после завершения CI/review цикла.

### FR-6: Защита от новых проблем

Все исправления по Issue #50 выполняются в ветке `bugfix/50`. До передачи MR каждый пакет изменений должен анализироваться именно из этой ветки и не должен перезаписывать baseline основной ветки.

Контур анализа `bugfix/50` должен:

- запускать BSL-анализ с канонической конфигурацией `.bsl-language-server.json` независимо от наличия coverage-артефактов;
- идентифицировать анализируемый commit SHA и ветку в отчёте;
- дожидаться завершения SonarQube Compute Engine task;
- сравнивать результат с зафиксированным baseline и целевой веткой;
- завершаться ошибкой при появлении новых BSL issues, новых BUG/VULNERABILITY или новых непроверенных Security Hotspots;
- публиковать ссылку на dashboard и краткий Markdown summary без токена и Authorization headers;
- не учитывать `coverage` и `new_coverage` при принятии решения в рамках этой спецификации.

Предпочтительный режим — native branch analysis с `sonar.branch.name=bugfix/50` и основной веткой как reference branch, если это поддерживается установленной редакцией SonarQube. Если branch analysis недоступен, использовать отдельный временный project key для `bugfix/50` и сравнивать его с сохранённым baseline. Запуск анализа ветки под project key основной ветки без branch isolation запрещён, поскольку он перезапишет состояние проекта `kafka-adapter`.

Существующий `release-sonar.yml` недостаточен как защита ветки: он вызывается release-контуром, зависит от coverage-артефактов и не блокирует результат по отдельным BSL-метрикам. Для `bugfix/50` нужен отдельный вызываемый workflow или скрипт проверки, который затем можно подключить к MR и основной ветке.

MR создаёт и запускает владелец репозитория. Результат реализации FR-6 до передачи владельцу включает:

1. воспроизводимый branch scan или точные команды его запуска;
2. автоматическую проверку BSL-условий без coverage;
3. Markdown summary для MR;
4. инструкцию по настройке required check.

После создания MR владелец запускает подготовленный контур. Issue #50 нельзя считать полностью проверенным до получения успешного результата этого MR check, но отсутствие созданного MR не блокирует подготовку кода и средств контроля в `bugfix/50`.

### FR-7: Учёт legacy baseline

До полной очистки существующего backlog применяется принцип Clean as You Code: новые issues запрещены, legacy исправляется пакетами. Issue #50 считается завершённым только после disposition всех исходных BSL issues, а не только после включения New Code gate.
### FR-8: Обязательное использование MCP

При анализе и изменении BSL необходимо использовать доступные MCP-инструменты, когда они применимы:

- EDT MCP — для чтения и точечного изменения модулей, навигации по объектам, проверки project problems и повторной валидации;
- code metadata/graph MCP — для поиска вызовов, экспортных методов и зависимостей до рефакторинга;
- syntax checker MCP — для синтаксической проверки изменённого BSL;
- code check MCP — для дополнительной проверки корректности, производительности, стандартов и читабельности;
- memory-bank MCP — для ведения baseline, решений, результатов пакетов и отклонений.

MCP не заменяет инженерный review. Сгенерированные рекомендации нельзя применять автоматически: их необходимо сопоставить с исходным кодом, метаданными, текущим стилем и результатами SonarQube. Если нужный MCP недоступен или завершается ошибкой, это фиксируется в отчёте пакета вместе с использованным fallback.

## Non-functional Requirements



- Публичные BSL API, фоновые операции, транзакционные границы и семантика очередей сохраняются, если изменение не оформлено отдельной спецификацией.
- Все конфигурационные исключения должны быть version-controlled и проверяемы code review.
- Секрет SonarQube хранится только в локальном `.codex/.env.sonar.local` рабочего каталога или в CI secrets; значение токена не документируется и не коммитится.
- Автоматизация должна выдавать rule, component, line и ссылку на issue без полного дампа исходного кода.
- Результаты анализа должны быть привязаны к commit SHA и analysis date.
- Сохранять текущие соглашения модуля: структуру областей, порядок методов, именование, язык комментариев, отступы, переносы и принятые идиомы BSL, если они не являются причиной подтверждённой проблемы.
- Улучшение метрики не является достаточным результатом: изменённый код должен быть не менее понятным и читабельным, чем исходный.
- Массовые изменения должны оставаться обозримыми для review; рекомендуемый предел определяется командой после первого пилотного пакета.

## Architecture and Design

Каноническим источником параметров BSL-диагностик остаётся `.bsl-language-server.json`; SonarQube использует его через `sonar.bsl.languageserver.overrideConfiguration=true`. Дублирование независимых наборов правил в IDE и CI не допускается.

Контур контроля:

```text
BSL source + .bsl-language-server.json
                 |
                 v
          Sonar Scanner
                 |
                 v
     SonarQube Compute Engine
                 |
                 v
      BSL New Code gate in CI
        |                    |
        v                    v
  merge allowed       merge blocked + summary
```

Общий Quality Gate может оставаться `ERROR` из-за исключённого из scope `new_coverage`. Поэтому BSL-gate должен проверять конкретные метрики и issues, а не интерпретировать общий статус без разбора условий. В будущем оба контура можно объединить отдельным решением.

ADR не требуется: сохраняются существующие границы SonarQube и BSL Language Server; добавляется операционный контроль качества.

## Implementation Plan


1. Получить из SonarQube полный список активных правил и список правил с открытыми issues; снять baseline, версии инструментов и привязку к commit.
2. Проверить 15 Security Hotspots и устранить подтверждённые риски.
3. Выполнить пилотный пакет CRITICAL BUG; измерить регрессии и стоимость review.
4. Исправить остальные BUG и ошибки разбора/потоков выполнения.
5. Пакетно снизить сложность и клиент-серверные проблемы в трёх наиболее нагруженных модулях.
6. Исправить массовые `LineLength`, `MagicNumber`, `MissingSpace` небольшими контекстными change sets с сохранением текущего стиля и ручной проверкой читабельности.
7. Оформить доказанные false positives точечными исключениями и зарегистрировать upstream defects анализатора.
8. Обработать оставшиеся документационные и style-only issues.
9. Добавить PR/main BSL-gate и защищённое использование SonarQube token.
10. Повторно проанализировать целевую ветку и сверить disposition ledger с исходным baseline.
11. Записать фактический результат, отклонения и остаточные риски в эту спецификацию и memory-bank.

## Compatibility and Migrations

Миграция данных не требуется.

Рефакторинг общих модулей может изменить внутренние точки расширения. Перед выделением процедур необходимо проверить экспортность, директивы компиляции, контекст клиента/сервера и внешние вызовы по репозиториям экосистемы.

Изменение quality profile или параметров диагностик может пересчитать baseline. Такое изменение оформляется отдельным пакетом с отчётом `before/after` по каждому затронутому правилу.

## Testing



Для каждого пакета обязательны:

1. BSL syntax/EDT validation изменённых модулей.
2. Повторный локальный или CI SonarQube analysis теми же версиями инструментов.
3. Проверка нулевого прироста issues вне целевого правила.
4. Unit-тесты YAxUnit для изменённой детерминированной логики.
5. UI-тесты Vanessa Automation для изменённых форм и клиент-серверных сценариев.
6. Kafka integration smoke tests для транспорта, фоновых обработчиков, очередей и таймаутов внешних ресурсов.
7. `git diff --check` и review отсутствия секретов.

Даже для форматных и однотипных правок требуется контекстный review изменённых фрагментов и проверка читаемости. Автоматическое применение замены ко всем совпадениям без просмотра результата запрещено. Для рефакторинга сложности и запросов в цикле сокращение тестов недопустимо.

Покрытие может продолжать собираться существующим pipeline, но его значение не является критерием приёмки этой спецификации.
### Ответственность за проверки

- В рамках реализации в `bugfix/50` выполняются статические проверки, BSL/EDT validation, SonarQube branch scan и проверки, не требующие запуска 1С.
- MR и проверки, требующие запуска 1С, выполняет владелец репозитория.
- Для 1С-проверок исполнитель изменений подготавливает перечень сценариев, ожидаемые результаты и затронутые модули.
- До получения результатов от владельца такие проверки отмечаются как `pending external verification`; они не считаются выполненными и не блокируют передачу ветки на MR, но остаются условием окончательной приёмки затронутого поведения.

## Risks

- Массовый рефакторинг крупных модулей может изменить транзакционность, порядок сообщений и конкуренцию фоновых заданий.
- Автоформатирование BSL может создать большие diff и скрыть логические изменения.
- Отключение массовых правил быстро уменьшит счётчик, но лишит проект полезного контроля.
- Результаты зависят от версий SonarQube, BSL-плагина и BSL Language Server; baseline нельзя сравнивать после их обновления без нормализации.

- Токен, сохранённый локально, остаётся секретом на рабочей станции; его необходимо ротировать при подозрении на раскрытие.
