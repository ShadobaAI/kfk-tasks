# Комбинированные метки обмена и устойчивые указатели

## Назначение и исходное состояние

Миллисекундная метка не различает события внутри одной миллисекунды. Сейчас `кфкОбработкаСобытийСлужебный` назначает одну метку строкам цикла регистрации, `кфкФоновыеОперацииСлужебный` использует дробное слагаемое при загрузке и общую метку изменения для пакета, а менеджеры регистров ставят сырое время при сбросе ошибки. Арифметика указателей и сроки хранения работают с миллисекундами. Формы и внешний лог преобразуют их в дату. Выгрузка логов с условием `МеткаИзмененияМС > &НачальнаяПозиция` пропускает остаток равных меток на границе порции (Issue #60).

Результат: новые записи получают уникальные в принятой области гарантии комбинированные метки; сохранённые значения преобразует отдельный метод после обновления ИБ. Рабочие обработчики используют только новый формат.

## Схема данных

| Регистр | Старое поле → новое поле | Вид | Новый тип |
| --- | --- | --- | --- |
| `кфкИсходящиеСообщения` | `ДатаРегистрацииМС` → `МеткаРегистрации` | измерение | `Число(30,0)` |
| `кфкИсходящиеСообщения` | `МеткаИзмененияМС` → `МеткаИзменения` | реквизит | `Число(30,0)` |
| `кфкВходящиеСообщения` | `ДатаЗагрузкиМС` → `МеткаЗагрузки` | измерение | `Число(30,0)` |
| `кфкВходящиеСообщения` | `МеткаИзмененияМС` → `МеткаИзменения` | реквизит | `Число(30,0)` |
| `кфкХэшСуммыСообщений` | `МеткаИзмененияМС` → `МеткаИзменения` | реквизит | `Число(30,0)` |
| `кфкОчередьПотоков` | `ВременнаяМетка` → `КомбинированнаяМетка` | измерение | `Число(30,0)` |
| `кфкПозицииОпераций` | `ВременнаяМетка` → `КомбинированнаяМетка` | ресурс | `Число(30,0)` |

Переименовать существующие объекты полей с сохранением их идентичности. `ДатаЗагрузки` и `ДатаРегистрации` типа `Дата` не менять. В `кфкПозицииОпераций` менять только указанный ресурс и формы; измерения `Идентификатор`, `Раздел` и реквизит `РазделПредставление` сохраняются. Ноль остаётся пустым указателем; ненулевая граничная метка может иметь нулевые компоненты сеанса и счётчика. Дополнительные поля позиции не вводить.

## Формат метки и общий API

`Метка = ВремяОт01012026МС * 10^18 + НомерСеанса * 10^8 + Счётчик`. Время — целые миллисекунды UTC от 01.01.2026 в диапазоне `1..999999999999`; номер сеанса — `1..9999999999`; счётчик — `1..99999999`. Число может занимать менее 30 десятичных знаков: компоненты извлекать арифметически, без разбора первых символов. `Начало2026МС = (Дата(2026,1,1) - Дата(1,1,1)) * 1000`; [материал 1С](https://its.1c.ru/db/content/metod8dev/src/developers/scalability/troubleshooting/i8105983.htm) подтверждает эпоху `ТекущаяУниверсальнаяДатаВМиллисекундах()` от 01.01.0001 UTC.

В серверном `кфкОбщегоНазначенияСлужебный` реализовать `НоваяКомбинированнаяМетка()`. Она использует `НомерСеансаИнформационнойБазы()` и параметр сеанса `кфкСчетчикКомбинированнойМетки`: первый выданный счётчик — `1`, каждый вызов выдаёт следующий, после `99999999` он переходит к `1`; смена миллисекунды его не сбрасывает. Последнюю метку/дату не хранить. За пределами любого компонента — явная ошибка до записи. Принятый инвариант: номер сеанса уникален в пределах одной миллисекунды, а один сеанс не выдаёт более `99999999` меток за неё; после перезапуска кластера используется новое время. Поддержка собственных параметров сеанса в расширении есть с [8.3.14.1565](https://wonderland.v8.1c.ru/blog/razvitie-mekhanizma-rasshireniy-konfiguratsii-14/); однократную выдачу счётчика при конкуренции проверить при реализации.

`КомбинированнаяМетка(Дата, НомерСеанса = Неопределено, Счётчик = Неопределено)` строит границу `[время][0][0]`, `[время][сеанс][0]` либо точную метку; счётчик без сеанса — ошибка. Параметр `Дата` — UTC-момент с точностью до секунды. Экспортные методы чтения, названные по результату согласно [#std647, п. 6.1](https://v8std.ru/std/647/):

| Метод | Результат |
| --- | --- |
| `МиллисекундыИзКомбинированнойМетки(Метка)` | `Начало2026МС + Цел(Метка / 10^18)` в прежней шкале миллисекунд; для нуля — `0` |
| `НомерСеансаИзКомбинированнойМетки(Метка)` | `Цел(Метка / 10^8) mod 10^10`; для нуля — `0` |
| `СчетчикИзКомбинированнойМетки(Метка)` | `Метка mod 10^8`; для нуля — `0` |
| `ДатаИзКомбинированнойМетки(Метка)` | `ДатаИзМС(МиллисекундыИзКомбинированнойМетки(Метка))` типа `Дата` с датой и временем; для нуля — пустая дата |

Для ненулевой метки проверять целочисленность и диапазон. Функции чтения не принимают старые миллисекундные значения. При реализации исправить неверный комментарий про Unix-эпоху у `ДатаМсВСтроку` без изменения её результата.

## Заполнение и указатели

Назначать новую метку каждой создаваемой записи и каждому изменению состояния: регистрация во всех ветвях, пакетная загрузка, сброс ошибки, сериализация, отправка, десериализация, возврат и хэш-суммы. Убрать дробное слагаемое загрузки. Копия первичной метки сообщения в `кфкОчередьПотоков` сохраняет точно то же число; для копии новую метку не генерировать. Обновить все записи и чтения в `кфкОбработкаСобытийСлужебный`, `кфкФоновыеОперацииСлужебный`, менеджерах двух регистров сообщений и связанных вызовах `кфкИнтеграцияСлужебный`/обработки `кфкИнтеграция`.

В `кфкФоновыеОперацииСлужебный` оставить подход `Указатели`: сортировку по полной метке, статусы потоков `0/1/-1`, фиксацию только завершённой непрерывной части и перемотку на `900000` мс. Неэкспортная `ГраничнаяКомбинированнаяМетка(Миллисекунды)` возвращает `(Миллисекунды - Начало2026МС) * 10^18` с нулевыми сеансом и счётчиком; до начала шкалы возвращает `0`. Она не вызывает генератор.

| Узел | Изменение |
| --- | --- |
| `УказательПогрешностьСмещения` | Возвращает интервал `900000` мс. |
| `УказательПустойВыборки` | Вычитает интервал из текущих миллисекунд и строит граничную метку. |
| `ПустаяТаблицаУказателейПотоков`, `ДобавитьУказательПотока` | Колонка `КомбинированнаяМетка` имеет тип `Число(30,0)` и хранит полную метку последней строки порции. |
| `ЗафиксироватьУказатели`, `ОбновитьСтатусУказателей` | Сохраняют логику завершения потоков и переход статуса `0 → 1`. |
| `ОбновитьУказательНачалаВыборки` | Без указателей сохраняет `Макс(текущая позиция, граница пустой выборки)`. С указателями берёт последнюю завершённую метку, извлекает миллисекунды, отматывает `900000` мс и сохраняет граничную метку. |

Сериализация, отправка и десериализация используют эту схему без ветвей старого формата. Прямые операции `±900000`, `±2000`, `−60000`, сроков хранения и сравнения разницы меток выполнять над извлечёнными миллисекундами; сравнение и сортировку полных меток сохранять числовыми. Это касается возврата в очередь, обработки дублей, удаления устаревших сообщений, очистки хэш-сумм и ограничения перед выгрузкой логов.

Внешнее логирование хранит в единственном ресурсе `кфкПозицииОпераций.КомбинированнаяМетка` метку изменения последней полностью выгруженной группы. Выбирать минимальную `МеткаИзменения` больше позиции и меньше временной границы, выгружать всю группу ограниченными порциями в порядке `(МеткаРегистрации/МеткаЗагрузки, КлючЗаписи)`. Внутригрупповой курсор временный; позицию продвигать только после успешной отправки всей группы. После сбоя группа читается заново. Тест Issue #60 должен проверять равные метки в обоих направлениях при размере порции `1`.

## Формы регистров

В формах списка и записи каждого из пяти регистров показывать полную метку без усечения и экспоненциального формата, рядом — три вычисляемых значения из неё. Названия колонок и полей:

| Сохранённая метка | Дата и время / номер сеанса / порядковый номер |
| --- | --- |
| `кфкИсходящиеСообщения.МеткаРегистрации` | `ДатаМеткиРегистрации` / `НомерСеансаМеткиРегистрации` / `ПорядковыйНомерМеткиРегистрации` |
| `кфкИсходящиеСообщения.МеткаИзменения` | `ДатаМеткиИзменения` / `НомерСеансаМеткиИзменения` / `ПорядковыйНомерМеткиИзменения` |
| `кфкВходящиеСообщения.МеткаЗагрузки` | `ДатаМеткиЗагрузки` / `НомерСеансаМеткиЗагрузки` / `ПорядковыйНомерМеткиЗагрузки` |
| `кфкВходящиеСообщения.МеткаИзменения` | `ДатаМеткиИзменения` / `НомерСеансаМеткиИзменения` / `ПорядковыйНомерМеткиИзменения` |
| `кфкХэшСуммыСообщений.МеткаИзменения` | `ДатаМеткиИзменения` / `НомерСеансаМеткиИзменения` / `ПорядковыйНомерМеткиИзменения` |
| `кфкОчередьПотоков.КомбинированнаяМетка` | `ДатаМетки` / `НомерСеансаМетки` / `ПорядковыйНомерМетки` |
| `кфкПозицииОпераций.КомбинированнаяМетка` | `ДатаМетки` / `НомерСеансаМетки` / `ПорядковыйНомерМетки` |

Все три значения вычислять общими методами; типы — `Дата` с временем, `Число(10,0)` и `Число(8,0)`. Для нуля показывать пустую дату и нулевые номера. Значения формы записи обновлять при чтении и после изменения метки, не сохранять их в регистре. `ДатаРегистрации` и `ДатаЗагрузки` типа `Дата` сохраняют прежний смысл. В двух списках сообщений старое вычисляемое `МеткаИзменения` пересоздать как `ДатаМеткиИзменения`; в очереди `Дата` — как `ДатаМетки`, в позициях `Указатель` — как `ДатаМетки`, а `УказательМС` заменить прямым полем `КомбинированнаяМетка`. В списке хэш-сумм добавить всю тройку. Пересоздать затронутые элементы форм и привязки, обновить DCS и сортировку. Заголовки с «мс» заменить на названия меток; ширина полного числа — до 30 знаков. Порядковый номер метки не является номером строки в пакете.

## Внешний JSON-лог

`ОбработчикВыгрузкиЛоговИсходящихСообщений` и `ОбработчикВыгрузкиЛоговВходящихСообщений` сохраняют `@timestamp` в прежнем строковом формате из миллисекунд первичной метки и остальные существующие поля, кроме `change_mark_ms`. Его заменяют:

| Ключ | Источник | Тип JSON |
| --- | --- | --- |
| `combined_mark` | Полная `МеткаИзменения` десятичной строкой без округления | строка |
| `change_mark_timestamp` | `ДатаМсВСтроку(МиллисекундыИзКомбинированнойМетки(МеткаИзменения))` | строка |
| `change_mark_session_number` | `НомерСеансаИзКомбинированнойМетки(МеткаИзменения)` | число |
| `change_mark_sequence_number` | `СчетчикИзКомбинированнойМетки(МеткаИзменения)` | число |

Исходящий лог дополнительно содержит `registration_mark_session_number` и `registration_mark_sequence_number` из `МеткаРегистрации`; входящий — `load_mark_session_number` и `load_mark_sequence_number` из `МеткаЗагрузки`. Входящий `load_date_ms` остаётся числом извлечённых миллисекунд. Строковый `id` строится из полной первичной метки и `КлючЗаписи`. Все ключи JSON, кроме существующего `@timestamp`, записывать по-английски в `snake_case`. `sequence_number` — циклический номер выдачи метки в сеансе, без сброса на границе пакета. Полную метку не выдавать JSON-числом из-за потери точности у потребителей.

## Обновление существующей ИБ

Перед обновлением включить существующую блокировку интеграции, остановить регламентные и интерактивные обработчики, дождаться завершения потоков и транзакций, сделать резервную копию. Расширение поля `Число(15)` до `Число(30,0)` само по себе сохраняет старые числа, но не меняет их смысл. До смены квалификатора проверить фактический тип и значения `ДатаЗагрузкиМС`: старый код вычисляет `НомерСообщения / 10000`. Если дробные ключи реально сохранены, переход к целому типу без потери данных невозможен; остановить обновление и решить этот случай до изменения схемы. На копии непустой ИБ проверить сохранность строк и значений после переименования и расширения.

После обновления конфигурации и до запуска любого обработчика пользователь вызывает на сервере экспортный метод `кфкИнтеграция.ОбновитьКомбинированныеМетки()`. `кфкИнтеграция` доступен на сервере и во внешнем соединении. Метод обрабатывает ненулевые старые значения `0 < Значение < 10^15` во всех семи полях, сохраняя их миллисекунду. Для самостоятельных старых меток он берёт номер текущего сеанса и свободный счётчик `1..99999999` в этой миллисекунде; занятые полные метки проверяет во всех затронутых регистрах, включая повторный запуск в том же или другом сеансе. Исторические метки не создавать через `НоваяКомбинированнаяМетка()`, которая подставляет текущее время. Недопустимое время, номер сеанса или исчерпание пула вызывают явную ошибку. Нуль сохранять только для пустых указателей и служебных строк очереди.

Для каждого сообщения мигрировать первичное измерение и `МеткаИзменения` с отдельной выдачей меток. Строку с новым ключом и связанные ненулевые строки `кфкОчередьПотоков` переносить в одной транзакции; очередь должна сохранить равенство с новой первичной меткой по `(КлючЗаписи, старая первичная метка)`. При отсутствующем или неоднозначном соответствии очереди завершить с диагностикой, не заменять значение произвольно. Нулевые строки распределения консьюмеров не менять. `кфкХэшСуммыСообщений.МеткаИзменения` мигрировать по тому же правилу выдачи. Старую ненулевую позицию `кфкПозицииОпераций` перевести в нижнюю границу той же миллисекунды `[МС][0][0]`, сохранив ключ `(Идентификатор, Раздел)`: записи граничной миллисекунды могут быть повторно прочитаны.

Метод повторно запускается после сбоя: уже новые значения пропускает, занятые метки учитывает, каждую связанную группу меняет атомарно. После обработки проверяет отсутствие старых ненулевых значений, сохранность числа строк и связей очереди, отсутствие коллизий новых ключей; сообщает числа преобразованных строк по регистрам. При ошибке блокировку не снимать. Пользователь возобновляет обработчики только после успешной проверки. Рабочие методы, формы и JSON не содержат ветвей чтения старых миллисекунд.

Миграция первичной метки меняет `id` внешнего лога. Повторная выгрузка ранее опубликованной граничной миллисекунды может создать дубли во внешнем хранилище с новым `id`; это учитывать при внедрении вместе с изменением схемы JSON.

## Реализация и проверка

1. В `kafka-adapter` проверить квалификаторы и все места использования семи полей, реализовать схему, API, указатели, формы, логирование и метод миграции через `kfk-edt`. После реализации обновить `docs/user/configuration/logging.md`, `docs/user/operations/queue-maintenance.md`, `docs/user/installation/updating.md` и при изменении описания потока `docs/overview/data-flow.md`.
