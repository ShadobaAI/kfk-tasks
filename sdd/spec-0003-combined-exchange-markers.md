# Комбинированные метки обмена и устойчивые указатели

## Назначение и исходное состояние

Миллисекундная метка не различает события внутри одной миллисекунды. До перехода регистрация использовала общую метку строк цикла, загрузка — дробное слагаемое и общую метку изменения пакета, сброс ошибки — сырое время. Выгрузка логов с условием `МеткаИзмененияМС > &НачальнаяПозиция` пропускала остаток равных меток на границе порции (Issue #60).

Результат: новые записи получают уникальные в принятой области гарантии комбинированные метки; сохранённые значения преобразует отдельный метод после обновления ИБ. Рабочие обработчики используют только новый формат.

## Схема данных

| Регистр | Старое поле → новое поле | Вид | Новый тип |
| --- | --- | --- | --- |
| `кфкИсходящиеСообщения` | `ДатаРегистрацииМС` → `МеткаРегистрации` | измерение | `Число(30,0)` |
| `кфкИсходящиеСообщения` | `МеткаИзмененияМС` → `МеткаИзменения` | реквизит | `Число(30,0)` |
| `кфкВходящиеСообщения` | `ДатаЗагрузкиМС` → `МеткаЗагрузки` | измерение | `Число(30,0)` |
| `кфкВходящиеСообщения` | `МеткаИзмененияМС` → `МеткаИзменения` | реквизит | `Число(30,0)` |
| `кфкХэшСуммыСообщений` | `МеткаИзмененияМС` → `МеткаИзменения` | реквизит | `Число(30,0)` |
| `кфкОчередьПотоков` | `ВременнаяМетка` → `КомбинированнаяМетка` | измерение | `Число(30,0)` |
| `кфкПозицииОпераций` | `ВременнаяМетка` → `КомбинированнаяМетка` | ресурс | `Число(30,0)` |

Все семь полей имеют неотрицательный тип `Число(30,0)`. Переименовать существующие объекты полей с сохранением их идентичности. `ДатаЗагрузки` и `ДатаРегистрации` типа `Дата` не менять. В `кфкПозицииОпераций` менять только указанный ресурс и формы; измерения `Идентификатор`, `Раздел` и реквизит `РазделПредставление` сохраняются. Ноль остаётся пустым указателем; ненулевая граничная метка может иметь нулевые компоненты сеанса и счётчика. Дополнительные поля позиции не вводить.

## Формат метки и общий API

`Метка = ВремяОт01012026МС * 10^18 + НомерСеанса * 10^8 + Счётчик`. Время — целые миллисекунды UTC от 01.01.2026 в диапазоне `1..999999999999`; номер сеанса — `1..9999999999`; счётчик — `1..99999999`. Число может занимать менее 30 десятичных знаков: компоненты извлекать арифметически, без разбора первых символов. `Начало2026МС = (Дата(2026,1,1) - Дата(1,1,1)) * 1000`; [материал 1С](https://its.1c.ru/db/content/metod8dev/src/developers/scalability/troubleshooting/i8105983.htm) подтверждает эпоху `ТекущаяУниверсальнаяДатаВМиллисекундах()` от 01.01.0001 UTC.

`кфкОбщегоНазначенияСлужебный.НоваяКомбинированнаяМетка()` использует `НомерСеансаИнформационнойБазы()` и параметр сеанса `кфкСчетчикКомбинированнойМетки`: первый выданный счётчик — `1`, каждый вызов выдаёт следующий, после `99999999` он переходит к `1`; смена миллисекунды его не сбрасывает. Последняя метка и дата не хранятся. Диапазоны компонентов задают допустимые значения; генератор не выполняет их явной проверки. Принятый инвариант: номер сеанса уникален в пределах одной миллисекунды, а один сеанс не выдаёт более `99999999` меток за неё; после перезапуска кластера используется новое время. Поддержка собственных параметров сеанса в расширении есть с [8.3.14.1565](https://wonderland.v8.1c.ru/blog/razvitie-mekhanizma-rasshireniy-konfiguratsii-14/); однократная выдача счётчика при конкуренции требует проверки в ИБ.

`ГраничнаяКомбинированнаяМетка(Значение)` принимает миллисекунды UTC от 01.01.0001 и возвращает `(Значение - Начало2026МС) * 10^18`: границу `[время][0][0]`. Конструктора с датой, номером сеанса и счётчиком в текущем API нет. Экспортные методы чтения:

| Метод | Результат |
| --- | --- |
| `МиллисекундыИзКомбинированнойМетки(Метка)` | `Начало2026МС + Цел(Метка / 10^18)` в прежней шкале миллисекунд; для нуля — `0` |
| `НомерСеансаИзКомбинированнойМетки(Метка)` | `Цел(Метка / 10^8) mod 10^10`; для нуля — `0` |
| `СчетчикИзКомбинированнойМетки(Метка)` | `Метка mod 10^8`; для нуля — `0` |
| `ДатаИзКомбинированнойМетки(Метка)` | `ДатаИзМС(МиллисекундыИзКомбинированнойМетки(Метка))` типа `Дата` с датой и временем; для нуля — пустая дата |

Методы чтения выполняют арифметическое разложение без проверки целочисленности, диапазона и старого формата; вызывающий код должен передавать корректную комбинированную метку. `ДатаИзКомбинированнойМетки` возвращает дату в часовом поясе сеанса. `ПредставлениеКомбинированнойМетки` возвращает строку с временем UTC, номером сеанса и счётчиком. Методы `МоментОтсчетаКомбинированнойМетки`, `ДатаОтсчетаКомбинированнойМетки` и три `Основание...КомбинированнойМетки` возвращают начало шкалы и основания компонентов. `ДатаМсВСтроку` получает миллисекунды от 01.01.0001 UTC и формирует строку ISO с миллисекундами и суффиксом `Z`.

## Заполнение и указатели

Регистрация во всех ветвях и пакетная загрузка выдают отдельную первичную метку каждой строке; начальная метка изменения совпадает с ней. Последующие изменения состояния при сбросе ошибки, сериализации, отправке, десериализации и возврате получают новые метки изменения. Дробное слагаемое загрузки не используется. Копия первичной метки сообщения в `кфкОчередьПотоков` сохраняет точно то же число. Исходящая хэш-сумма получает метку изменения отправленного сообщения; входящая — новую метку при сохранении хэш-суммы.

В `кфкФоновыеОперацииСлужебный` оставить подход `Указатели`: сортировку по полной метке, статусы потоков `0/1/-1`, фиксацию только завершённой непрерывной части и перемотку на `900000` мс. Граничная метка вычисляется как `(Миллисекунды - Начало2026МС) * 10^18` с нулевыми сеансом и счётчиком, без вызова генератора. Обе даты выражены в миллисекундах от 0001 года; `Начало2026МС = 63902822400000`. Для текущих дат после начала 2026 года разность положительна; ограничение через `Макс(0, ...)` не требуется. Возврат нуля для дат до начала шкалы не является требованием.

| Узел | Изменение |
| --- | --- |
| `УказательПогрешностьСмещения` | Возвращает интервал `900000` мс. |
| `УказательПустойВыборки` | Вычитает интервал из текущих миллисекунд и строит граничную метку. |
| `ПустаяТаблицаУказателейПотоков`, `ДобавитьУказательПотока` | Колонка `КомбинированнаяМетка` имеет тип `Число(30,0)` и хранит полную метку последней строки порции. |
| `ЗафиксироватьУказатели`, `ОбновитьСтатусУказателей` | Сохраняют логику завершения потоков и переход статуса `0 → 1`. |
| `ОбновитьУказательНачалаВыборки` | Без указателей сохраняет `Макс(текущая позиция, граница пустой выборки)`. С указателями берёт последнюю завершённую метку, извлекает миллисекунды, отматывает `900000` мс и сохраняет граничную метку. |

Сериализация, отправка и десериализация используют эту схему без ветвей старого формата. Прямые операции `±900000`, `±2000`, `−60000`, сроков хранения и сравнения разницы меток выполнять над извлечёнными миллисекундами; сравнение и сортировку полных меток сохранять числовыми. Это касается возврата в очередь, обработки дублей, удаления устаревших сообщений, очистки хэш-сумм и ограничения перед выгрузкой логов.

Внешнее логирование хранит в единственном ресурсе `кфкПозицииОпераций.КомбинированнаяМетка` метку изменения последней строки успешно отправленной порции. Выбирать обычные ограниченные порции по `МеткаИзменения > Позиция` и `МеткаИзменения < ВерхняяВременнаяГраница`, сортировать по полной комбинированной метке изменения. После успешной HTTP-отправки сохранять последнюю метку; при исключении сохранённая позиция не меняется. Обход групп равных меток и временные курсоры убрать. Сохранить существующую минутную задержку, продвижение позиции при длительной пустой выборке и новые преобразования меток для дат и JSON. Предпосылка — отдельная метка изменения каждой строки, включая исторические строки после миграции. Для Issue #60 проверять разные полные метки одной миллисекунды в обоих направлениях при размере порции `1`.

## Формы регистров

В формах списка и записи каждого из пяти регистров показывать полную метку без усечения и экспоненциального формата, рядом — дату и время, номер сеанса и порядковый номер. Реквизиты форм записи:

| Сохранённая метка | Дата и время / номер сеанса / порядковый номер |
| --- | --- |
| `кфкИсходящиеСообщения.МеткаРегистрации` | `МеткаРегистрацииДата` / `МеткаРегистрацииСеанс` / `МеткаРегистрацииНомер` |
| `кфкИсходящиеСообщения.МеткаИзменения` | `МеткаИзмененияДата` / `МеткаИзмененияСеанс` / `МеткаИзмененияНомер` |
| `кфкВходящиеСообщения.МеткаЗагрузки` | `МеткаЗагрузкиДата` / `МеткаЗагрузкиСеанс` / `МеткаЗагрузкиНомер` |
| `кфкВходящиеСообщения.МеткаИзменения` | `МеткаИзмененияДата` / `МеткаИзмененияСеанс` / `МеткаИзмененияНомер` |
| `кфкХэшСуммыСообщений.МеткаИзменения` | `МеткаИзмененияДата` / `МеткаИзмененияСеанс` / `МеткаИзмененияНомер` |
| `кфкОчередьПотоков.КомбинированнаяМетка` | `КомбинированнаяМеткаДата` / `КомбинированнаяМеткаСеанс` / `КомбинированнаяМеткаНомер` |
| `кфкПозицииОпераций.КомбинированнаяМетка` | `КомбинированнаяМеткаДата` / `КомбинированнаяМеткаСеанс` / `КомбинированнаяМеткаНомер` |

Все три значения вычислять общими методами; типы — `Дата` с временем, `Число(10,0)` и `Число(8,0)`. Для нуля показывать пустую дату и нулевые номера. Значения формы записи обновлять при чтении и после изменения метки, не сохранять их в регистре. `ДатаРегистрации` и `ДатаЗагрузки` типа `Дата` сохраняют прежний смысл. В двух списках сообщений старое вычисляемое `МеткаИзменения` пересоздать как `ДатаМеткиИзменения`; в очереди `Дата` — как `ДатаМетки`, в позициях `Указатель` — как `ДатаМетки`, а `УказательМС` заменить прямым полем `КомбинированнаяМетка`. В списке хэш-сумм добавить всю тройку. Пересоздать затронутые элементы форм и привязки, обновить DCS и сортировку. Заголовки с «мс» заменить на названия меток; ширина полного числа — до 30 знаков. Порядковый номер метки не является номером строки в пакете.

## Внешний JSON-лог

`ОбработчикВыгрузкиЛоговИсходящихСообщений` и `ОбработчикВыгрузкиЛоговВходящихСообщений` сохраняют `@timestamp` в прежнем строковом формате из миллисекунд первичной метки и остальные существующие поля, кроме `change_mark_ms`. Его заменяют:

| Ключ | Источник | Тип JSON |
| --- | --- | --- |
| `combined_mark` | Полная `МеткаИзменения` десятичной строкой без округления | строка |
| `change_mark_timestamp` | `ДатаМсВСтроку(МиллисекундыИзКомбинированнойМетки(МеткаИзменения))` | строка |
| `change_mark_session_number` | `НомерСеансаИзКомбинированнойМетки(МеткаИзменения)` | число |
| `change_mark_sequence_number` | `СчетчикИзКомбинированнойМетки(МеткаИзменения)` | число |

Исходящий лог дополнительно содержит `registration_mark_session_number` и `registration_mark_sequence_number` из `МеткаРегистрации`; входящий — `load_mark_session_number` и `load_mark_sequence_number` из `МеткаЗагрузки`. Входящий `load_date_ms` остаётся числом извлечённых миллисекунд. Строковый `id` строится из полной первичной метки и `КлючЗаписи`. Все ключи JSON, кроме существующего `@timestamp`, записывать по-английски в `snake_case`. `sequence_number` — циклический номер выдачи метки в сеансе, без сброса на границе пакета. Полную метку не выдавать JSON-числом из-за потери точности у потребителей.

## Обновление существующей ИБ

Экспортная процедура `кфкИнтеграция.ОбновитьКомбинированныеМетки()` обрабатывает позиции, хэш-суммы, исходящие и входящие сообщения четырьмя самостоятельными циклами. Историческая метка строится как `(СтарыеМС - Начало2026МС) * 10^18 + Счётчик`, без текущего времени и номера сеанса. Счётчик `1..99999999` циклический, сквозной для каждого регистра между порциями одного вызова; при новом вызове он начинается заново. Обоим полям сообщения выдаётся один порядковый номер. Позиции тоже получают ненулевой счётчик. Занятость меток и диапазоны исторических дат не проверяются.

`кфкОчередьПотоков` не проверяется и не преобразуется. Уже полные дубли автоматически не исправляются. Размер порции — до 10000 строк. Итогового контроля числа строк и отчёта по регистрам нет. `НоваяИсторическаяМетка` осталась неэкспортным неиспользуемым методом; её проверки не участвуют в миграции. Общего `МигрироватьИсторическиеМеткиРегистра` в текущем модуле нет.

Перед обновлением включить существующую блокировку интеграции, остановить регламентные и интерактивные обработчики, дождаться завершения потоков и транзакций, сделать резервную копию. Расширение поля `Число(15)` до `Число(30,0)` само по себе сохраняет старые числа, но не меняет их смысл. До смены квалификатора проверить фактический тип и значения `ДатаЗагрузкиМС`: старый код вычисляет `НомерСообщения / 10000`. Если дробные ключи реально сохранены, переход к целому типу без потери данных невозможен; остановить обновление и решить этот случай до изменения схемы. На копии непустой ИБ проверить сохранность строк и значений после переименования и расширения.

`кфкИнтеграция` доступен на сервере и во внешнем соединении. Процедура намеренно включает привилегированный режим, устанавливает блокировку интеграции, если её ещё нет, и ожидает завершения активных потоков адаптера. Отбор позиций использует `0 < КомбинированнаяМетка < 10^18`; у хэш-сумм и сообщений проверяется только `МеткаИзменения < 10^18`, без нижнего ограничения. По уточнению пользователя старые метки в `кфкХэшСуммыСообщений`, `кфкИсходящиеСообщения` и `кфкВходящиеСообщения` содержат только ненулевые даты в миллисекундах; дополнительное исключение нуля для них не требуется. Это принятый инвариант входных данных, а не результат проверки ИБ. В выбранной строке сообщения преобразуются оба поля без проверки их формата. Значения до начала 2026 года не помещаются в неотрицательную шкалу. Проверка миграции на копии непустой ИБ остаётся отдельной проверкой внедрения.

Удаление старых ключей сообщений и добавление строк с новыми ключами выполняются одной транзакцией порции. Позиции и хэш-суммы записываются в режиме обновления. Ключ позиции `(Идентификатор, Раздел)` сохраняется; записи исторической миллисекунды могут быть прочитаны повторно. До обновления нужно разобрать старые строки очереди: копии меток в ней не меняются вместе с первичными метками сообщений.

При повторном вызове счётчик сбрасывается, занятые значения не учитываются. Проверка коллизий при повторе исключена из требований по уточнению пользователя. При ошибке блокировка остаётся установленной; после успеха снимается только блокировка, установленная самой процедурой. Перед возобновлением обмена нужно проверить отсутствие старых ненулевых значений, сохранность числа строк и уникальность меток изменения каждого направления на копии ИБ. Рабочие методы, формы и JSON не содержат ветвей чтения старых миллисекунд.

Экспортный метод остаётся процедурой без возвращаемого значения. Во время выполнения нужно исключить параллельный запуск миграции и любые другие записи.

Если ранее была запущена ошибочная миграция с одинаковыми полными граничными метками, повторный вызов их не изменит. До запуска порционной выгрузки проверить уникальность `МеткаИзменения` в каждом из двух регистров сообщений. При дублях оставить обмен заблокированным и отдельно согласовать исправление данных; преобразование уже полных меток не входит в текущий алгоритм.

Миграция первичной метки меняет `id` внешнего лога. Повторная выгрузка ранее опубликованной граничной миллисекунды может создать дубли во внешнем хранилище с новым `id`; это учитывать при внедрении вместе с изменением схемы JSON.

- В `кфкФоновыеОперацииСлужебный` обновлены загрузка, переходы состояний, очередь, указатели, интервалы, очистка и внешний JSON. Логи выгружаются полными группами равных меток с продвижением позиции только после успешной отправки группы; запросы групп проверены EDT.
- В `кфкИнтеграция` добавлен экспортный `ОбновитьКомбинированныеМетки()` для остановленного обмена. Запросы миграции проверены EDT; выполнение на ИБ остаётся за пользователем.
- Проверка свободного исторического счётчика обращается ко всем семи полям для каждой новой метки. На большой ИБ миграция может выполняться долго; оценить время на копии ИБ до продуктивного обновления.
- В списках и формах записи пяти регистров показаны полные метки и три вычисляемых составляющих. Все десять форм прошли `validate_form_model`, диагностика EDT по пяти регистрам не сообщает проблем. Из-за ограничения редактора DCS старые внутренние имена неиспользуемых полей схемы сохранились; отображаемые поля и запросы используют новый формат.
- Документы адаптера по логированию, очередям, обновлению и потоку данных обновлены. Unit-тесты будут обновлены после проверки пользователем в ИБ.

1. В `kafka-adapter` проверить квалификаторы и все места использования семи полей, реализовать схему, API, указатели, формы, логирование и метод миграции через `kfk-edt`. После реализации обновить `docs/user/configuration/logging.md`, `docs/user/operations/queue-maintenance.md`, `docs/user/installation/updating.md` и при изменении описания потока `docs/overview/data-flow.md`. Инструкция обновления задаёт порядок «остановка → резервная копия → обновление схемы → вызов метода миграции → проверка → запуск».
2. Следующий этап — обновление существующих YAxUnit-тестов в `kafka-adapter-tests-unit` по разделу «Итог ревью и переход к обновлению тестов». Результаты запуска, проверки в ИБ и оставшиеся ограничения зафиксировать отдельно. Исторические сценарии, исключённые из принятого scope, не восстанавливать как требования к реализации.
