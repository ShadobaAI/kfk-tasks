# Переразмещение логики объектов спецификаций КФК

## Краткое описание

Переразместить предметную и повторяющуюся серверную логику объектов `кфк*` из модулей форм и перегруженных модулей менеджеров в естественных владельцев. Основное место прикладной логики — неглобальные серверные общие модули с узкой предметной ответственностью. В формах и менеджерах остаются только предусмотренные платформой точки входа, UI-логика и небольшие объектные адаптеры, когда именно объект метаданных является естественным владельцем операции. Добавить расширяемую проверку спецификации перед фиксацией версии и минимальные правила технических имён. Сохранить существующую архитектуру конструктора AsyncAPI и результат формирования YAML для корректных данных. Существующие сигнатуры и точки входа не считаются ограничением, если их изменение необходимо для корректного размещения кода и все потребители изменяются согласованно.

## Контекст

Расширение `KFK` формирует произвольные XDTO-контракты и зафиксированные версии спецификаций. Зафиксированная версия может выгружаться в различные форматы. Текущий `кфкКонструкторAsyncAPI.СформироватьAsyncAPI` является точкой формирования YAML, а документ `кфкВерсияСпецификации` фиксирует состав и версии объектов спецификации.

Анализ через `conv-edt` выявил смешение UI и предметной логики в формах, форматонезависимой подготовки снимка и YAML-сериализации, а также повторяющийся каркас расчёта повышения версии в нескольких менеджерах справочников.

## Проблема

1. `ФормаПодбораПолей` справочника `кфкТипыДанныхСпецификации` выполняет запросы, преобразует типы КД в типы спецификации и формирует предметную модель добавляемых полей.
2. `ФормаЭлемента` того же справочника содержит операцию записи объекта, не относящуюся к UI-сценарию формы.
3. `кфкКонструкторAsyncAPI.СформироватьAsyncAPI` одновременно восстанавливает форматонезависимый снимок версии и сериализует его в YAML.
4. В шести менеджерах справочников дублируется общий каркас `ПолучитьВидПовышения`.
5. В `УдалитьИзмененияУдаленныхНовинок` поле `ВидПовышения` сравнивается со значением перечисления `кфкВидыИзмененияДанных`, хотя по метаданным поле имеет тип `кфкВидыПовышенияВерсий`.
6. Перед созданием версии отсутствует единая проверка текущей спецификации. Некорректные шаблоны и образованные ими имена обнаруживаются только при формировании YAML либо попадают в некорректный документ.
7. Формирование имён по шаблонам находится внутри YAML-сериализатора, хотя оно требуется до создания версии и является общей предметной операцией.

## Цель

- Оставить в формах UI-обработчики, работу с данными формы, UI-специфичную серверную подготовку данных и необходимые клиент-серверные адаптеры.
- Перенести самостоятельные переиспользуемые предметные сервисы из форм и перегруженных менеджеров в серверные общие модули с узкой ответственностью.
- Оставить за менеджерами только объектные операции, обязательные обработчики и тонкие адаптеры к предметным сервисам.
- Исключить дублирование общего алгоритма повышения версии.
- Отделить получение зафиксированного снимка от форматной YAML-сериализации.
- Исправить несогласованное условие запроса удаления изменений удалённых новых объектов.
- Сохранить внешнее поведение для корректных спецификаций и общую архитектуру конструктора, не сохраняя ошибочные границы модулей только ради совместимости внутренних сигнатур. Выпуск некорректной спецификации намеренно блокируется.
- Не связывать предметные сервисы с формой, обработкой или конкретным способом запуска, чтобы они могли использоваться интерактивно, в фоне и через HTTP без дублирования реализации.
- Не создавать версию при наличии ошибок проверки; вернуть пользователю полный перечень найденных ошибок одним результатом.
- Предоставить понятную точку добавления новых правил без изменения механизма выпуска версии и форматных сервисов.

## Не входит в задачу

- Изменение структуры метаданных хранения спецификаций и версий.
- Изменение формата AsyncAPI YAML.
- Создание универсального registry, plugin framework или динамической регистрации форматов выгрузки.
- Реализация выгрузки в Markdown или другие новые форматы.
- Полная проверка документа по JSON Schema AsyncAPI внешним parser/validator.
- Проверка существования топиков или политик конкретного Kafka-кластера через сетевое подключение.
- Автоматическое исправление, транслитерация или нормализация пользовательских имён.
- Изменение пользовательских сценариев форм.
- Изменение базовой конфигурации `conversion/КД`.
- Рефакторинг заимствованных объектов без префикса `кфк`.

## Область изменений

- Справочники `кфкКаналыСпецификации`, `кфкПеречисленияСпецификации`, `кфкПриложенияСпецификаций`, `кфкПримерыСообщенийСпецификации`, `кфкСпецификации`, `кфкТипыДанныхСпецификации`, `кфкТипыЗначенийСпецификации`.
- Обработка `кфкКонструкторAsyncAPI`.
- Документ `кфкВерсияСпецификации`.
- Регистры сведений `кфкВерсииСпецификации`, `кфкИзмененияОбъектовСпецификаций`.
- Перечисления `кфкВидыИзмененияДанных`, `кфкВидыПовышенияВерсий`.
- Определяемый тип `кфкКомпонентСпецификации`, роль `кфкДобавлениеИзменениеСпецификации` и подсистема `кфкКонтрактыСпецификации` только в части проверки ссылок и прав; их структура не изменяется.
- Новый неглобальный серверный общий модуль `кфкРаботаСоСпецификациями`. Версионирование, получение данных версии, формирование AsyncAPI, подбор полей, работа с техническими именами и проверка спецификации разделяются внутри него функциональными областями.

## Функциональные требования

1. Размещение и сигнатура `СформироватьAsyncAPI` определяются ответственностью кода, а не текущим местом вызова. При изменении имени, владельца или параметров все статические и строковые вызовы изменяются атомарно.
2. Формируемые имя файла и двоичные данные YAML не изменяются для одинаковой зафиксированной версии, если изменение формата не требуется для исправления подтверждённого дефекта.
3. Серверный сервис выгрузки версий предоставляет форматонезависимый метод получения данных зафиксированной версии. Менеджер документа не дублирует этот API без платформенной необходимости.
4. Серверный сервис AsyncAPI получает подготовленную модель версии и отвечает только за AsyncAPI/YAML-представление.
5. Формирование представления зафиксированной версии не читает текущее состояние редактируемых объектов спецификации: результат строится только по сохранённому снимку версии.
6. Подготовка данных подбора полей и сопоставление типов выполняются вне модуля формы.
7. Форма подбора сохраняет существующие команды, пометки и представление дерева.
8. Экспортные `ПолучитьВидПовышения` остаются в менеджерах объектов как объектные адаптеры для динамического вызова из регистра изменений.
9. Общая обработка событий создания, удаления, восстановления и индексов повышения не дублируется в менеджерах.
10. Объектно-специфичные правила классификации реквизитов остаются в менеджерах соответствующих справочников.
11. `УдалитьИзмененияУдаленныхНовинок` отбирает записи по виду изменения `Удаление`, а не сравнивает несовместимые типы перечислений.
12. Проверка спецификации выполняется непосредственно перед расчётом и записью новой версии, до изменения регистра изменений и создания документа.
13. При наличии ошибок документ версии и записи регистров не создаются и не изменяются; вызывающий код получает одно исключение с полным перечнем ошибок.
14. Результат каждого правила содержит как минимум код правила, объект, имя поля и текст ошибки. Порядок ошибок детерминирован.
15. Минимальный набор правил проверяет:
    - заполненность и допустимые символы `кфкТипыДанныхСпецификации.Код`;
    - заполненность и допустимые символы `кфкПеречисленияСпецификации.Наименование` как ключа `components/schemas`;
    - заполненность ссылки канала на тип данных и допустимость фактически сформированного `ИмяКанала`;
    - синтаксис шаблонов `АдресТопика`, `ИмяКанала`, `ИмяОперации`, `ИмяСообщения`, `ИмяСообщенияКанала`, `ИмяСхемы`, включая разрешённые теги `%ТИП%` и `%ОПЕРАЦИЯ%` и их параметры регистра/разделителя;
    - фактически сформированные для активных объектов адреса топиков и идентификаторы каналов, операций, сообщений и схем;
    - уникальность сформированных ключей в пределах соответствующих коллекций AsyncAPI и отсутствие коллизий ключей схем типов данных и перечислений.
16. Адрес Kafka topic непустой, не равен `.` или `..`, имеет длину не более 249 символов и состоит только из ASCII-букв, цифр, `.`, `_`, `-` согласно проверке Apache Kafka `Topic.validate`.
17. Технические идентификаторы AsyncAPI непустые, не равны `.` или `..` и состоят из ASCII-букв, цифр, `.`, `_`, `-`; это консервативное проектное ограничение для безопасных YAML-ключей, JSON Pointer и совместимости инструментов, а не несуществующее требование AsyncAPI о формате всех идентификаторов.
18. Проверяются только актуальные, не помеченные на удаление объекты, входящие в выпускаемую спецификацию.
19. При интерактивном выпуске ожидаемые ошибки проверки выводятся одним локализованным пользовательским сообщением без внутреннего кода правила и технического стека. Для каждой ошибки указываются объект, понятное имя поля, некорректное значение, причина и способ исправления, когда эти данные применимы.
20. Ошибки производных имён не дублируют ошибку исходного идентификатора: если код типа данных или имя перечисления некорректны, зависящие от них имена схем, топиков, каналов, операций и сообщений проверяются после исправления исходного значения. Независимые ошибки продолжают возвращаться одним результатом.
21. Неожиданные программные ошибки не маскируются пользовательской обработкой проверки и выводятся стандартным механизмом с технической диагностикой.

## Нефункциональные требования

- Все изменения `src/**` выполняются только через `conv-edt`.
- Соблюдаются `v8std` #440, #455, #469, #630 и #636.
- Новый общий модуль неглобальный, непривилегированный и недоступный для прямого вызова с клиента.
- Каждый новый общий модуль имеет одну явную предметную ответственность; общие модули не используются как формальное хранилище несвязанного кода.
- Выбор между общим модулем и модулем менеджера определяется связностью: независимый переиспользуемый сервис размещается в общем модуле, операция конкретного типа объекта и обязательная точка входа платформы — в менеджере.
- Имена процедур, функций, параметров и переменных отражают предметное назначение; общие слова без уточнения не используются.
- Экспортные методы документируются по принятому в проекте формату.
- Не добавляются скрытые fallback-механизмы и не ослабляются проверки, права или транзакционные гарантии.
- Внутренние и служебные сигнатуры могут изменяться для исправления границ ответственности. Все потребители должны быть найдены через EDT и изменены согласованно; неиспользуемые совместимые обёртки не сохраняются.
- Структуры, передаваемые между сервисом снимка и форматными сервисами, имеют документированный состав и не содержат `ДанныеФормы*`, элементов формы, объектов обработки или иных UI-зависимостей.
- Форматные сервисы не хранят состояние между вызовами и не зависят от пользовательского сеанса.
- Правила проверки не выполняют запись данных, не показывают UI и добавляют найденные проблемы только в переданную коллекцию результата.
- Новое правило добавляется отдельной процедурой с одним явным подключением в последовательность правил; строковое динамическое выполнение произвольного кода не используется.

## Архитектура и дизайн

### Принцип размещения кода

Цель рефакторинга — не минимальное количество строк в формах и менеджерах само по себе, а однозначное владение кодом:

- модуль формы содержит обработчики интерфейса, состояние формы, преобразование `ДанныеФормы*` и тонкие вызовы серверного API;
- модуль менеджера содержит обязательные обработчики платформы, операции уровня конкретного объекта метаданных и тонкие адаптеры, необходимые для динамического полиморфного вызова;
- неглобальный серверный общий модуль `кфкРаботаСоСпецификациями` содержит не зависящую от формы и экземпляра объекта предметную логику, запросы предметного сервиса и повторно используемые алгоритмы;
- модуль объекта содержит проверки и изменение состояния записываемого экземпляра, когда операция является частью его жизненного цикла;
- функциональная область форматного сервиса содержит только построение конкретного внешнего представления.

Перенос выполняется по связности и ответственности. Код не переносится в общий модуль только ради уменьшения менеджера: это создаёт процедурный контейнер без самостоятельной ответственности и противоречит требованиям сопровождаемости и назначению общих модулей по #std469.

### Снимок версии

Форматонезависимая подготовка снимка выделяется в самостоятельную функциональную область `ДанныеВерсий` общего модуля `кфкРаботаСоСпецификациями`. Менеджер документа `кфкВерсияСпецификации` сохраняет только тонкую объектную точку входа, если она требуется платформой или является естественной операцией типа документа. Сервис проверяет проведение документа и возвращает форматонезависимую структуру с версией, автором и снимками компонентов спецификации.

AsyncAPI/YAML-сериализация выделяется в функциональную область `ФормированиеAsyncAPI` общего модуля `кфкРаботаСоСпецификациями`. Она получает модель из области `ДанныеВерсий` и выполняет только форматную работу. В неё переносятся `СтрокаYAML`, `ДобавитьКаналы`, `ДобавитьОперация`, `ДобавитьКомпоненты` и связанные форматные функции. Разбор шаблонов и формирование имён размещаются в области `ИменаСпецификаций`. Обработка `кфкКонструкторAsyncAPI` остаётся пользовательским сценарием конструктора и содержит форму и только необходимую оркестрацию запуска.

Такое выделение не создаёт универсальную фабрику форматов: публичный метод AsyncAPI может вызываться из обработки, фонового задания или будущих регламентных сценариев без зависимости от объекта обработки.

### Границы для дальнейшего развития

Снимок зафиксированной версии является единым внутренним источником данных для представлений версии. AsyncAPI/YAML — первый форматный потребитель этого снимка. Последующие форматы оформляются самостоятельными функциональными областями с отдельными точками входа и не должны повторно реализовывать чтение истории данных или зависеть от обработки `кфкКонструкторAsyncAPI`.

HTTP-сервис, фоновое задание и форма рассматриваются как разные адаптеры запуска одного серверного API. Текущее изменение не создаёт HTTP-интерфейс, Markdown-экспорт или реестр форматов, но границы модулей не должны препятствовать их последующему добавлению.

Проверки корректности спецификации являются отдельной ответственностью от получения снимка и сериализации. Создаётся расширяемая последовательность правил, но не универсальная динамическая plugin-платформа. Форматный сервис не должен содержать правила, которые относятся ко всем форматам. Специфичные ограничения ключей AsyncAPI/YAML подключаются перед сериализацией без изменения сервиса снимка.

В рамках расширенного объёма создаётся минимальный механизм правил проверки спецификации. Он не зависит от формы и документа версии, собирает все ошибки за один проход и имеет явный список последовательно вызываемых правил. Каждое правило оформляется отдельной процедурой и добавляет структурированные ошибки через единый служебный метод. Такой подход оставляет простую точку расширения без динамического вызова строковых обработчиков и без преждевременного plugin framework.

Сервисы анализа связей типов, каналов и перечислений не объединяются с форматной сериализацией. Если текущий перенос выявит такие запросы в формах, они размещаются по предметной ответственности и проектируются для повторного использования, но новые пользовательские функции просмотра мест использования в эту задачу не входят.

### Проверка спецификации и технических имён

В общем модуле `кфкРаботаСоСпецификациями` создаётся область `ПроверкаСпецификаций`. Публичная операция возвращает массив структурированных ошибок без исключения, чтобы правила можно было использовать из формы, фонового задания и будущего HTTP API. Ожидаемые ошибки проверки не преобразуются в исключение: результат проверки включается в результат операции выпуска версии.

Сбор необходимых данных выполняется одним предметным запросом или минимальным числом пакетных запросов, без запроса на каждый объект. Контекст проверки содержит спецификацию, активные типы данных, перечисления и каналы.

Формирование имён по шаблонам переносится из менеджера `кфкКонструкторAsyncAPI` в область `ИменаСпецификаций`. Один и тот же метод используется валидатором и AsyncAPI-сериализатором, поэтому проверяется именно то значение, которое будет выгружено.

Правила различают назначение значения:

- `АдресТопика` после подстановки тегов проверяется по Apache Kafka `Topic.validate`;
- `ИмяКанала`, `ИмяОперации`, `ИмяСообщения`, `ИмяСообщенияКанала`, `ИмяСхемы`, код типа и имя перечисления проверяются как технические идентификаторы проекта;
- `кфкКаналыСпецификации.Наименование` остаётся человекочитаемым заголовком AsyncAPI `title` и не входит в новые правила технических имён.

Шаблоны уровня канала имеют приоритет над шаблонами спецификации так же, как в текущем формировании YAML. Проверка учитывает оба значения `send` и `receive` в фактическом контексте канала. Неизвестный или синтаксически повреждённый тег является отдельной ошибкой шаблона, а не маскируется общей ошибкой итогового имени.

### Контракт выпуска версии и вывод ошибок проверки

`Документы.кфкВерсияСпецификации.СформироватьВерсиюСпецификации` является функцией и возвращает структуру со свойствами:

- `Успешно` — `Булево`; `Истина` только после успешной записи и проведения версии;
- `ВерсияСпецификации` — ссылка на созданный документ либо `Неопределено`, если версия не выпущена;
- `Ошибки` — массив структур ошибок проверки.

Каждый элемент массива `Ошибки` содержит `КодПравила`, `Объект`, `ИмяПоля` и `ТекстОшибки`. `КодПравила` сохраняется в машинном результате для диагностики и автоматических потребителей, но не выводится пользователю. При наличии хотя бы одной ошибки функция возвращает `Успешно = Ложь`, `ВерсияСпецификации = Неопределено` и полный массив ошибок до любых изменений данных выпуска.

Фоновый вызов выполняется как функция. `ЗавершениеВыпускаВерсии` получает результат через временное хранилище и различает два класса неуспеха:

- ожидаемые ошибки проверки формируются в форме в компактный нумерованный отчёт: одна строка заголовка и одна строка на ошибку с объектом, понятным представлением поля и причиной; служебные коды правил и стек вызовов не показываются;
- неожиданный технический сбой фоновой операции продолжает выводиться стандартным механизмом `ИнформацияОбОшибке`.

Если `Успешно = Ложь`, но массив ошибок пуст, форма выводит отдельное сообщение о некорректном результате операции. Список версий обновляется только при `Успешно = Истина`.

### Подбор полей

Подготовка данных подбора выделяется в неглобальный серверный предметный сервис. Он получает свойства объекта конфигурации, исключает уже существующие элементы и сопоставляет типы КД с типами спецификации. Менеджеры `кфкТипыДанныхСпецификации` и `кфкПеречисленияСпецификации` сохраняют методы только для операций, действительно принадлежащих конкретному типу объекта; транзитные обёртки без платформенной или полиморфной необходимости не создаются.

Форма получает готовое `ДеревоЗначений` или другую сериализуемую структуру и загружает её в реквизит формы. Работа с элементами формы, пометками пользователя и `ДанныеФормыДерево` остаётся в форме.

### Повышение версии

В служебном программном интерфейсе `кфкРаботаСоСпецификациями` создаётся область `Версионирование`. Она содержит общие операции механизма: обработку записи истории для нового/удалённого/восстановленного объекта, перевод вида повышения в индекс и объединение индексов.

Экспортные `ПолучитьВидПовышения` остаются в менеджерах справочников. Они передают общей реализации параметры общего сценария и содержат объектно-специфичную классификацию изменённых реквизитов.

Обработчики `ОбработкаПослеЗаписиВерсийИсторииДанных` остаются в менеджерах объектов как обязательные тонкие точки входа платформы.

### Ограничение архитектуры конструктора

Обработка `кфкКонструкторAsyncAPI`, её форма и менеджер не заменяются универсальным конструктором форматов. Новые абстрактные фабрики, registry форматов и динамические обработчики не создаются. Разрешено изменить внутренние точки входа и сигнатуры, если это устраняет неправильную границу ответственности; все вызовы при этом изменяются согласованно.

## План реализации

1. Зафиксировать точечный baseline EDT-диагностик и текущие структуры затрагиваемых модулей.
2. Создать через `conv-edt` общий модуль версионирования с корректными свойствами выполнения.
3. Вынести общий каркас повышения версии, сохранив объектные адаптеры и специфичные правила.
4. Перенести подготовку данных подбора и независимые предметные операции формы элемента в профильные серверные общие модули; оставить в менеджерах только операции конкретного типа объекта и обязательные точки входа.
5. Вынести получение форматонезависимого снимка и AsyncAPI/YAML-сериализацию в два самостоятельных серверных сервиса; оставить в менеджерах документа и обработки только обоснованные платформенные или объектные точки входа.
6. Вынести разбор шаблонов и формирование имён в самостоятельный серверный сервис и перевести на него сериализатор.
7. Реализовать структурированный результат проверки и минимальный набор правил технических имён.
8. Встроить блокирующую проверку перед любыми изменениями при выпуске версии.
9. Исправить поле отбора в `УдалитьИзмененияУдаленныхНовинок`.
10. Проверить платформенные API и типы через документацию и content assist `conv-edt`.
11. Провалидировать изменённые запросы.
12. Выполнить точечную ревалидацию объектов, EDT-диагностики и доступные интеграционные проверки Conversion Data/XDTO.
13. Зафиксировать фактический результат и отклонения в SDD.

## Совместимость и миграция

- Миграция данных не требуется.
- Состав объектов хранения и типы реквизитов не изменяются.
- Фоновый вызов остаётся работоспособным. Его строковое имя, владелец и параметры могут быть изменены вместе с вызывающим кодом, если это требуется итоговым размещением метода.
- Формирование AsyncAPI может быть вызвано без создания или открытия обработки `кфкКонструкторAsyncAPI`.
- Результат формирования YAML должен остаться байтово идентичным при одинаковых данных и окружении, за исключением уже недетерминированных платформенных представлений, если они существуют.
- Новые экспортные методы общих модулей и оставшиеся служебные методы менеджеров размещаются в `ПрограммныйИнтерфейс` или `СлужебныйПрограммныйИнтерфейс` согласно кругу потребителей.
- Ранее сохранённая спецификация с некорректными техническими именами больше не сможет выпустить новую версию до исправления данных. Автоматическая миграция или исправление таких имён не выполняется.

## Проверка

- `conv-edt`: `revalidate_objects` для всех изменённых FQN.
- `conv-edt`: `get_project_errors` до и после изменений с точным фильтром объектов.
- `conv-edt`: `validate_query` для каждого изменённого запроса.
- Проверка структуры модулей по #std455.
- Проверка нового общего модуля по #std469 и отсутствия клиентского/привилегированного контекста.
- Проверка форм по #std630 и клиент-серверных вызовов по #std636.
- Сравнение YAML до и после на доступной зафиксированной версии спецификации, если тестовая информационная база и данные доступны.
- Релевантные Conversion Data/XDTO integration checks при доступном окружении.
- Позитивные и негативные проверки имён: пустое значение, кириллица, пробел, `/`, `~`, `.`, `..`, длина topic 249/250, допустимые `.`, `_`, `-`.
- Проверка корректных и повреждённых тегов шаблонов, подстановки `%ТИП%`/`%ОПЕРАЦИЯ%`, наследования шаблона спецификации и переопределения каналом.
- Проверка коллизий сформированных channel/operation/message/schema keys и отсутствия записанного документа/регистров при ошибках.

## Риски

- Изменение структуры возвращаемой модели снимка может изменить YAML; контракт модели должен быть локальным и проверяться сравнением результата.
- Перенос логики формы может изменить типы `ДанныеФормы*`; серверный предметный сервис не должен принимать или возвращать клиентские типы данных формы.
- Чрезмерный вынос объектных правил повышения версии в общий модуль ухудшит сопровождаемость; в общий модуль переносится только инвариантный каркас.
- Фоновый вызов зависит от строкового имени экспортного метода; при переименовании или переносе строковый вызов должен быть найден и изменён в той же логической операции.
- Исправление отбора удалённых новинок меняет ранее ошибочное поведение и требует отдельной проверки сценария добавления с последующим удалением до выпуска версии.
- Новые ограничения могут выявить ранее допустимые кириллические или содержащие пробелы технические имена; это намеренное блокирующее изменение для новых версий.
- Проверка только исходного шаблона дала бы ложноположительный результат при некорректном `Код`; поэтому правила обязаны проверять итоговые значения после подстановки.
- `Наименование` канала намеренно не проверяется новым механизмом технических имён: текущий сериализатор помещает его в человекочитаемый `title`.

## Критерии приёмки

1. Общая архитектура конструктора спецификации сохранена; нет registry/factory форматов.
2. Точка фонового формирования AsyncAPI и все её потребители согласованы по владельцу, имени, параметрам и результату; устаревшие обёртки без потребителей отсутствуют.
3. Форматонезависимое восстановление снимка и AsyncAPI/YAML-сериализация отсутствуют в менеджере `кфкКонструкторAsyncAPI` и реализованы самостоятельными функциональными областями `ДанныеВерсий` и `ФормированиеAsyncAPI` общего модуля `кфкРаботаСоСпецификациями`; в обработке остаётся только UI-оркестрация и необходимые платформенные точки входа.
4. В `ФормаПодбораПолей` отсутствуют предметные запросы и сопоставление типов КД с типами спецификации.
5. Операция изменения пометки удаления отсутствует в модуле формы элемента; получение свойств конфигурации для единственного UI-сценария остаётся служебной серверной логикой формы и не образует отдельный API менеджера или общего модуля.
6. Общий каркас повышения версии реализован один раз; специфичные правила реквизитов остаются в менеджерах объектов.
7. `кфкРаботаСоСпецификациями` соответствует #std455 и #std469: верхний уровень содержит только `ПрограммныйИнтерфейс`, `СлужебныйПрограммныйИнтерфейс` и `СлужебныеПроцедурыИФункции`, а предметные обязанности разделены вложенными функциональными областями; модуль не доступен для прямого вызова с клиента.
8. Запрос удаления изменений удалённых новинок использует поле `ВидИзменений` с типом `кфкВидыИзмененияДанных`.
9. Новых EDT-диагностик на изменённых объектах нет.
10. Изменённые запросы проходят `validate_query`.
11. При доступном окружении YAML до и после совпадает для одной зафиксированной версии.
12. Для каждой оставшейся существенной процедуры в форме или менеджере зафиксирована естественная зависимость от UI, жизненного цикла, типа объекта либо обязательного платформенного вызова; транзитных обёрток без такой причины нет.
13. Серверный API получения снимка и формирования AsyncAPI вызывается без открытия формы и без экземпляра обработки.
14. Область `ФормированиеAsyncAPI` не обращается к текущему состоянию объектов спецификации и не содержит универсальных правил валидации, не относящихся непосредственно к AsyncAPI/YAML.
15. Выпуск версии блокируется до записи данных при любой ошибке проверки; функция возвращает `Успешно = Ложь`, пустую `ВерсияСпецификации` и полный массив структур ошибок.
16. Минимальные правила имён, шаблонов, итоговых значений и коллизий реализованы в серверном сервисе и покрывают перечисленные граничные случаи.
17. AsyncAPI-сериализатор и валидатор используют один сервис разбора шаблонов и формирования имён.
18. Добавление нового правила требует отдельной процедуры правила и одного явного подключения; код выпуска версии и формы при этом не изменяется.
19. При ошибке проверки пользователь получает один компактный нумерованный отчёт без `KFK-*` кодов и стека вызовов. Отчёт занимает одну строку заголовка и по одной строке на ошибку; каждая запись содержит проверяемый объект, понятное имя поля, фактическое некорректное значение и действие для исправления.
20. Один некорректный исходный код не порождает повторные сообщения для каждого зависящего от него производного имени.
21. Для ошибки, не относящейся к проверке спецификации, сохраняется стандартный технический вывод `ИнформацияОбОшибке`.
22. При успешном выпуске функция возвращает `Успешно = Истина`, ссылку `ВерсияСпецификации` и пустой массив `Ошибки`; список версий в форме обновляется только для такого результата.

## Открытые вопросы

Нет блокирующих вопросов. Имена новых служебных методов могут быть уточнены по ближайшим проектным примерам без изменения описанных границ ответственности.

## Результат реализации

- Создан один неглобальный непривилегированный серверный общий модуль `кфкРаботаСоСпецификациями`. Узконаправленные общие модули удалены после переноса методов и проверки отсутствия ссылок.
- Структура `кфкРаботаСоСпецификациями` приведена к #std455: верхнеуровневые области `ПрограммныйИнтерфейс`, `СлужебныйПрограммныйИнтерфейс` и `СлужебныеПроцедурыИФункции`; внутри них используются функциональные области `Версионирование`, `ДанныеВерсий`, `ФормированиеAsyncAPI`, `ПодборПолей`, `ИменаСпецификаций` и `ПроверкаСпецификаций`.
- Общая обработка событий истории и агрегация индексов повышения вынесены из шести менеджеров; объектно-специфичная классификация и экспортные `ПолучитьВидПовышения` сохранены в менеджерах.
- Из `ФормаПодбораПолей` вынесены предметные запросы, построение дерева и сопоставление типов. В форме оставлены UI-обработчики и два контекстных серверных адаптера. В `ФормаЭлемента` сохранена UI-специфичная серверная подготовка свойств конфигурации; операция записи пометки удаления вынесена в менеджер справочника.
- Получение снимка зафиксированной версии отделено от AsyncAPI/YAML-сериализации функциональными областями. Снимок и иерархия типов строятся только по сохранённым версиям `ИсторияДанных`; фоновая точка вызова переведена на `кфкРаботаСоСпецификациями.СформироватьAsyncAPIВерсии`.
- Разбор шаблонов и формирование технических имён вынесены в единый сервис, используемый сериализатором и проверкой. Реализованы проверки шаблонов, кодов типов, имён перечислений, итоговых topic/channel/operation/message/schema keys и их коллизий.
- `СформироватьВерсиюСпецификации` переведена в функцию. Она выполняет проверку перед любыми изменениями и возвращает структуру `Успешно, ВерсияСпецификации, Ошибки`: при ошибках — `Успешно = Ложь` и массив структур, после успешной записи — `Успешно = Истина` и ссылка на созданную версию.
- `ПроверитьСпецификацию` возвращает массив структур `КодПравила, Объект, ИмяПоля, ТекстОшибки`; ожидаемая ошибка проверки больше не передаётся через исключение.
- `ЗавершениеВыпускаВерсии` получает результат фоновой функции и выводит ошибки проверки одним компактным нумерованным отчётом без внутренних кодов правил и технического стека: одна строка заголовка и одна строка на ошибку. Строка содержит объект, понятное имя поля, фактическое некорректное значение и рекомендацию по исправлению; каскадные ошибки производных имён подавляются до исправления исходного идентификатора. Неожиданные ошибки продолжают выводиться стандартным техническим механизмом.
