# Составная числовая метка и порционная выгрузка логов

## Контекст

Миллисекундное время не различает записи, созданные в одной миллисекунде. Старые первичные метки входят в ключи сообщений, метки изменения управляют выборкой и внешним логированием, а очередь потоков и позиции операций содержат их копии. Отбор внешнего лога по `МеткаИзмененияМС > Позиция` пропускает часть строк, если равная метка попала на границу порции (Issue #60).

## Решение

Технические поля пяти регистров, перечисленные в [SPEC-0003](../sdd/spec-0003-combined-exchange-markers.md), получают тип `Число(30,0)` и имена без суффикса `МС`; оба поля `ВременнаяМетка` становятся `КомбинированнаяМетка`. В `кфкПозицииОпераций` меняется только ресурс и его формы. Существующие объекты полей переименовываются без удаления.

Формат метки — `[12 миллисекунды от 01.01.2026 UTC][10 номер сеанса][8 счётчик]`, численно `Время * 10^18 + НомерСеанса * 10^8 + Счётчик`. `кфкОбщегоНазначенияСлужебный.НоваяКомбинированнаяМетка()` берёт номер сеанса ИБ и инкрементирует параметр сеанса `кфкСчетчикКомбинированнойМетки` при каждом вызове; после `99999999` счётчик переходит к `1`. Последнюю метку или дату не хранить. Гарантия уникальности опирается на принятые инварианты: номера сеансов различны в одной миллисекунде, один сеанс выдаёт не более `99999999` меток за неё, после перезапуска кластера используется новое время. Наличие собственного параметра сеанса в расширении подтверждено для [1С 8.3.14.1565](https://wonderland.v8.1c.ru/blog/razvitie-mekhanizma-rasshireniy-konfiguratsii-14/); однократность инкремента при конкуренции проверяется при реализации.

Арифметика длительностей выполняется над миллисекундами, извлечёнными из метки. Общие экспортные методы возвращают миллисекунды, дату и время, номер сеанса и счётчик. Алгоритм `Указатели` сохраняет статусы потоков `0/1/-1` и 15-минутную перемотку, записывая числовую границу `[время][0][0]`. Позиция внешнего лога остаётся одним ресурсом. Оба направления выбирают обычные ограниченные порции по `МеткаИзменения > Позиция` и ниже верхней временной границы, сортируя по полной метке изменения. После успешной отправки сохраняется метка последней строки порции. Обход групп равных меток и временные курсоры исключаются: каждой строке выдаётся собственная метка изменения, в том числе при миграции исторических данных. Преобразования меток для дат и JSON сохраняются.

Переход существующей ИБ выполняется отдельной серверной процедурой `кфкИнтеграция.ОбновитьКомбинированныеМетки()` при остановленных писателях, до запуска обработчиков. Историческое время сохраняется, компонент сеанса равен нулю. Рабочие запросы, формы и логирование используют новый формат без ветвей чтения старых миллисекунд. Очередь потоков не преобразуется, поэтому до обновления её старые строки должны быть разобраны.

Текущая миграция обрабатывает четыре регистра самостоятельными циклами и строит `(СтарыеМС - Начало2026МС) * 10^18 + Счётчик`. Циклический счётчик `1..99999999` сквозной для каждого регистра между порциями одного вызова; оба поля сообщения используют один порядковый номер, позиции тоже получают счётчик. Проверки занятости и диапазона дат в вызываемом коде отсутствуют; `НоваяИсторическаяМетка` не вызывается. Проверка коллизий при повторном вызове исключена из требований по уточнению пользователя. Привилегированный режим миграции является намеренным решением. Точный алгоритм и ограничения описаны в SPEC-0003; предпосылка порционной выгрузки — уникальность меток изменения каждого направления — сохраняется.

Решение от 2026-09-29 предусматривало обход групп равных меток. Решение от 2026-10-01 заменяет его обычными порциями после восстановления отдельной выдачи метки каждой строке во всех четырёх методах регистрации исходящих (подтверждено пользователем через EDT). Состояние реализации и незавершённые проверки записаны в SPEC-0003.

Формы списка и записи показывают полную метку и вычисленные дату с временем, номер сеанса и порядковый номер. Во внешнем JSON сохраняются `@timestamp` и `load_date_ms`; `change_mark_ms` заменяется четырьмя полями метки изменения, а из первичной метки добавляются номер сеанса и порядковый номер. Полная метка передаётся десятичной строкой, остальные новые ключи имеют английские имена в `snake_case`. Точный контракт полей и проверок задан в SPEC-0003.

Временная граница вычисляется как `(Значение - МоментОтсчетаКомбинированнойМетки()) * ОснованиеВремениКомбинированнойМетки()`. Входное значение и момент отсчёта выражены в миллисекундах от 0001 года; момент отсчёта равен `63902822400000`. Для текущих дат после начала 2026 года разность положительна. Исторические значения до начала шкалы несовместимы с неотрицательным типом поля. Состояние реализации и результаты ревью отражены в SPEC-0003, эксплуатационные ограничения — в инструкции обновления.

## Последствия и проверка

### Принятые отклонения от исходного решения

Уточнения пользователя и итоговая реализация от 2026-10-01 задают контракт следующего этапа:

- Обычные ограниченные порции заменяют обход групп равных меток. Для каждого направления требуется уникальность полной метки изменения; сценарий Issue #60 использует разные метки одной миллисекунды.
- Миграция не переносит и не проверяет `кфкОчередьПотоков`; старые строки очереди разбираются до обновления. Автоматический контроль количества строк и отчёт о преобразованиях не входят в реализацию.
- Исторические метки имеют нулевой номер сеанса и циклический счётчик регистра. Оба поля сообщения используют один порядковый номер, позиции тоже получают счётчик. Общий обработчик регистров и проверка занятости меток не требуются; используются четыре отдельных цикла. Коллизии при повторном вызове исключены из требований по прямому уточнению пользователя.
- Привилегированный запуск процедуры миграции предусмотрен намеренно; отдельная проверка прав вызывающего пользователя не требуется в принятом scope.
- По подтверждённому пользователем инварианту в сообщениях и хэш-суммах старые метки содержат даты в миллисекундах и не равны нулю. Исключение нуля необходимо только для позиций и реализовано. Проверка фактических данных ИБ в рамках ревью не выполнялась.

Обновление тестов выполняется по актуальному контракту SPEC-0003. Исторические требования о переносе очереди, свободных номерах при повторе и раздельной выдаче счётчика двум полям сообщения не должны становиться критериями приёмки тестового этапа.

- До смены типа проверить фактическую дробность старых первичных ключей: перевод сохранённой дроби в `Число(30,0)` без потери значения невозможен. Миграцию проверить на копии непустой ИБ, включая равные старые миллисекунды, связи очереди, позиции и повторный запуск после сбоя.
- Поскольку первичная метка входит в `id` внешнего лога, повторная выгрузка граничной миллисекунды после миграции может создать дубли с новым `id`; это учитывать при внедрении во внешнее хранилище.
- Уже полные дубли после прежней ошибочной миграции не исправляются повторным вызовом. До запуска порционной выгрузки подтвердить уникальность меток изменения каждого направления в ИБ; при дублях требуется отдельное исправление данных.
- Следующий этап — обновление и запуск существующих YAxUnit-тестов в `kafka-adapter-tests-unit` по актуальному контракту SPEC-0003. Проверить выдачу и разложение меток, переход счётчика, указатели, интервалы и JSON; для Issue #60 — разные полные метки одной миллисекунды в обоих направлениях при порции `1`. Проверки в ИБ, конкурентной выдачи и производительности миграции остаются незавершёнными и фиксируются отдельно; завершение ревью не означает их успешного прохождения.
